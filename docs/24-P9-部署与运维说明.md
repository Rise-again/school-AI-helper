# P9 部署与运维说明

> 2026-11-15。P9-01/02/06 落地说明。

## 1. 进程托管（P9-01，保持现状）

用户决定 **不引入 systemd/watchdog**（D-27），继续使用：

```bash
cd /hy-tmp/campus/app
bash scripts/start.sh            # all | vllm | models | backend
bash scripts/stop.sh             # all | vllm | models | backend
```

- 容器 PID1 是 `docker-init`，没有 systemd；supervisord 只管 jupyter/sshd。
- 进程为 `setsid nohup`，pid 在 `/hy-tmp/campus/run/*.pid`，日志在 `/hy-tmp/campus/logs/`。
- **重启实例后需手动 `bash scripts/start.sh`**；`start.sh backend` 会自动拉起 MySQL。
- 服务以 root 运行（课程项目接受；如后续要建 `campus` 服务用户，需整体 chown venv/data，属额外改动）。
- vLLM 冷启动 1–3 分钟；演示前先预热一次。

## 2. 对外访问（P9-02）

- 内网 `0.0.0.0:8080`，平台自定义服务映射到 `http://i-2.gpushare.com:44368/`（HTTP，无 TLS）。
- 前端 `dist` 由 FastAPI 托管，前后端同端口；`uvicorn` 启动参数带 `--proxy-headers --forwarded-allow-ips=*`。
- 实测：公网首页 200、`curl -N` 逐块 SSE（meta 1.55s，后续 delta 连续）；**20MB 上传成功**，但经平台代理耗时 **165s**（约 127KB/s，平台带宽限制，记录为已知约束）。
- 公网 `/metrics` 404（仅本机）；`/readyz` 四项。

## 3. 监控与巡检（P9-06）

每日执行：

```bash
/hy-tmp/campus/venvs/web/bin/python scripts/p9_healthcheck.py
```

检查项与阈值：

| 项 | 阈值/说明 |
|---|---|
| `/readyz` | mysql/llm/models/chroma 四项必须 ok |
| 进程 | vllm/models/backend 的 pid 必须存活 |
| 磁盘 `/`、`/hy-tmp` | 使用率 ≥80% 告警 |
| 显存 | 容器内 `nvidia-smi` 使用率 ≥90% 告警（D-26；平台监控页 0/24GB 不可信） |
| AnySearch 配额 | 剩余 <200 告警 |
| 事件循环延迟 / RSS | 记录 `event_loop.lag_ms`、`process.rss_mb` |
| 日志轮转 | backend/vllm/model-service 超过 100MB 时 copytruncate 到 `.1` |

输出写入 `/hy-tmp/campus/logs/health.log`；退出码 1 表示有告警。

## 4. 每日巡检清单

1. `curl -s 127.0.0.1:8080/readyz` 四项 ok；
2. 跑 `p9_healthcheck.py`，看 warnings；
3. 看 `/hy-tmp/campus/logs/backend.log` 最近 ERROR/WARN；
4. 看 `nvidia-smi` 显存与 `df -h /hy-tmp`；
5. 看 AnySearch 配额余量（healthcheck 输出）；
6. 需要时 `bash scripts/backup.sh` 备份到 OSS。

## 5. 已知限制

- 无 systemd，崩溃不会自动拉起；用户已知并接受。
- 平台实例监控 GPU 读数不可信，以容器内为准。
- 20MB 上传很慢，演示不要现场传大文件；提前入库。
