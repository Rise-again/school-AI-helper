# P7 性能报告（压测 · 调优 · 可观测性）

> 2026-11-15，LoRA 版（`campus-lora`）现网实测。对应计划 v1.18 的 P7-01/02/03/04/05；P7-06 故障演练另行出报告。
> 环境：恒源云 RTX 4090 24GB（驱动 570 / CUDA 12.8），Ubuntu 22.04.5 容器，128 核 / 503GB 内存；后端单 worker，端口 8080；vLLM 8001；model-service 8002；MySQL/Chroma 同机。

## 1. 结论

| 项目 | 验收口径 | 实测 | 结论 |
|---|---|---|---|
| 6 并发首字 | P95 ≤3s | **P95 2.58s**（P50 1.46s） | ✅ |
| 6 并发生成 | 错误率 <1% | **0%**（20/20） | ✅ |
| 10 并发 | 只验证不崩溃 | 错误率 **0%**，P95 首字 6.29s | ✅ 不崩溃；时延不作承诺 |
| 显存 | vLLM ≤19GiB、总量 ≤22GiB | vLLM **18.4GiB**，model-service 3.2GiB，合计 **21.6GiB**（24GiB 卡） | ✅ |
| 事件循环 | 无阻塞告警 | 最大延迟 **5.4ms**，无 >200ms 告警 | ✅ |
| 空闲内存 | 稳定 | 后端 RSS **173.5MB** | ✅ |
| 限流 | 超限 100% 429、提示明确 | 第 11 次请求 **429 + `Retry-After: 5` + code 5001** | ✅ |
| 故障演练 | 六场景可降级 | 待做 | ⏳ P7-06 |

旧口径里“10 并发 P95 ≤5s”与“仅作不崩溃验证”自相矛盾，本报告按后者执行：**6 并发是唯一时延承诺，10 并发只记录不承诺**。相关文档已同步（计划 M7/P7-04、需求基线 F6）。

## 2. P7-01 服务异步化

### 2.1 改动

| 位置 | 改动 | 目的 |
|---|---|---|
| `integrations/llm_client.py`、`rag/embedding.py`、`rag/rerank.py`、`rag/ocr.py`、`integrations/anysearch.py` | 每个客户端持有一个复用的 `httpx.AsyncClient`，设置连接上限与 keep-alive；生命周期结束时 `aclose()` | 消除每次问答/检索新建 TCP/TLS 的开销，6 并发下连接可复用 |
| `integrations/anysearch.py` | 网页正文的 BeautifulSoup 解析改用 `asyncio.to_thread` | 30 万字符 HTML 解析是 CPU 活，避免阻塞事件循环 |
| `rag/indexer.py` | `chunk_pages` 下放线程池 | 大文档切片（逐句估算 token）会占几十到几百毫秒 |
| `main.py` | 启动每秒采样事件循环延迟与 RSS；关闭时取消监控并关闭全部 HTTP 客户端 | 给“无阻塞/内存稳定”留下可核查数据 |
| 既有实现复核 | `Retriever` 的 Chroma 查询、解析器的 PDF/MarkItDown、OCR 读文件、知识库文件写入/删除、教务 SDK 调用均已在 `asyncio.to_thread` 中 | 确认没有遗漏的同步阻塞点 |

### 2.2 证据

压测期间 `/metrics` 的 `event_loop.lag_ms`：最小 -0.79ms、P50 0.24ms、P95 1.04ms、最大 **5.4ms**；日志无 `event_loop_lag` 告警。`process.rss_mb` = **173.5MB**，压测前后无增长趋势。

## 3. P7-02 限流与排队

### 3.1 设计

- **登录用户**：按 `user_id` 每分钟最多 10 次；
- **访客**：按 `visitor_id` cookie（HttpOnly、SameSite=Lax、30 天）每分钟最多 10 次；
- **IP 维度**：仅当来源不是共享网关时参与。2026-11-15 实测平台代理把所有公网来源折叠成 `172.17.0.1`，且 `X-Forwarded-For` 可被客户端伪造，因此不能按 IP 限流（D-16）；
- **排队**：同时生成 8 个（对齐 vLLM `max-num-seqs`），超出进入有界队列（最多 3 个、最长 8 秒）；队列满或等待超时返回 429 + `Retry-After: 5`；
- **超限记录**：只写结构化日志与内存指标，不建表、不迁移（D-17）。

### 3.2 实测

- 同一访客连续请求：第 1–10 次 200，第 11 次 **429**，响应头 `retry-after: 5`，Body `{"code":5001,...}`；
- 同一访客带伪造 `X-Forwarded-For: 9.9.9.9` 仍为 429，证明不能绕过；
- 新访客（无 cookie）立即 200，未误伤；
- 10 并发压测 20 请求：0 个 429，队列等待 P95 约 3.0s、最大 6.2s，均在被 8 秒上限内完成。

## 4. P7-03 参数与显存

### 4.1 参数表（未调整）

| 参数 | 值 | 说明 |
|---|---|---|
| `--gpu-memory-utilization` | 0.75 | vLLM 预留给权重与 KV cache 约 18.4GiB；给 model-service 留 3.2GiB |
| `--max-model-len` | 6144 | 5 轮历史 + 5 条证据（单条约 500 token） |
| `--max-num-seqs` | 8 | 与后端排队上限对齐 |
| `--enforce-eager` | 开 | 省显存；LoRA 推理已比基座慢约一倍 |
| `--max-lora-rank` | 16 | `campus-lora` adapter |

### 4.2 为什么没调参

6 并发 P95 已达标（2.58s），显存也在新口径内（vLLM 18.4 ≤19GiB，总量 21.6 ≤22GiB）。继续加 `gpu_memory_utilization` 或 `max-num-seqs` 会挤压 model-service 显存、且需要重启 vLLM 承担冷启动风险；10 并发时延本来就不作承诺，收益不抵风险。四级降级顺序保留不变：关 eager → 重排挪 CPU → OCR 挪 CPU → `max-model-len` 降回 4096。

## 6. P7-05 可观测性

### 6.1 出口

- `GET /metrics`：**仅服务器本机可访问**（经公网代理返回 404），JSON 内含 counters/timers/gauges、`chat_gate` 与当日搜索配额；
- 结构化日志：每行 JSON，带 `trace_id`；关键事件见下表。

### 6.2 指标清单

| 类型 | 名称 | 用途 |
|---|---|---|
| counter | `http.requests`、`http.status.*` | 请求量与状态码分布 |
| counter | `chat.requests`、`chat.model_down` | 问答总量与模型不可用次数 |
| counter | `rate_limit.blocked.{user,guest,ip}` | 各维度限流次数 |
| counter | `chat.queue_rejected`、`chat.queue_timeout` | 队列满/等待超时 |
| counter | `app_error.*` | 业务错误码分布 |
| counter | `retrieval.requests`、`retrieval.kb_hit`、`retrieval.web_hit`、`retrieval.empty` | 检索命中与空结果 |
| timer | `http.latency_ms` | 非 SSE 接口延迟 |
| timer | `chat.first_delta_ms`、`chat.total_ms`、`chat.queue_wait_ms` | 首字、总时长、排队等待 |
| timer | `event_loop.lag_ms` | 事件循环阻塞 |
| timer | `retrieval.kb_top`、`retrieval.kept` | 知识库最高分、保留证据数 |
| gauge | `process.rss_mb` | 进程内存水位 |
| gauge | `chat_gate.active/queued` | 当前生成与排队数 |
| gauge | `search_quota.used/limit/remaining` | 当日 AnySearch 配额 |

关键日志：`request`（方法/路径/状态/耗时）、`slow_request`（非 SSE 超过 3s）、`chat_metrics`（queued/first_delta/total/intent/evidence/kb/web/kept/model_down）、`agent_trace`（意图、关键词、节点）、`rate_limited`（scope/key/limit）、`queue_waited/rejected/timeout`、`search_failed/search_quota_exceeded`。

### 6.3 故障定位（5 分钟内）

1. `curl -s 127.0.0.1:8080/readyz` 看 mysql/llm/models 三项；
2. `curl -s 127.0.0.1:8080/metrics` 看错误码、限流、排队、事件循环延迟、RSS、搜索配额；
3. 按 `trace_id` grep `/hy-tmp/campus/logs/backend.log`，看 `agent_trace` 与 `chat_metrics` 定位到路由/检索/生成/落库哪一段；
4. 模型/OCR 问题再看 `/hy-tmp/campus/logs/vllm.log`、`model-service.log`。

## 7. 遗留与风险

- 10 并发首字 6.29s，超过旧口径 5s；已按“不作承诺”记录，若答辩要求 10 并发时延需另做预算评估。

- 当前无 systemd，vLLM 崩溃不会自动拉起；P7-06 恢复路径为手动 `scripts/start.sh`（D-19），P9-01 再托管。
- 搜索配额当日已用 66/1800（压测前），压测题目均为知识库可答，未消耗配额。
- 显存按 GiB 计：24GiB 卡上 vLLM 18.4GiB + model-service 3.2GiB = 21.6GiB，剩约 2.4GiB 余量。
